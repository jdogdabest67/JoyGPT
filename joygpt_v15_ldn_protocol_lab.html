1 · Version-matched facts

Important boundary: public protocol documentation describes general Nintendo protocol generations, not a complete validated capture of Splatoon 2 or Splatoon 3 v11.3.0 on Switch 2. Do not treat a protocol version match as proof of every game field.

Splatoon 2

Documented: Switchbrew's version history records Pia 5.9.3 in the v5.2.0 update. The community LAN protocol docs include older Pia 5.x layouts, including legacy browse messages and encrypted session messages.

Not established here: the exact LDN protocol selection used by each current Splatoon 2 build on Switch 2; exact game-specific application-data fields; successful interoperability with a phone.

Status: version-family lead, not a complete current packet specification.

Splatoon 3 v11.3.0

Documented: Pia 6.32.3 was introduced in v10.0.0; v11.3.0 notes report no SDK version update while the main executable changed. v10.0.0 also introduced use of LDN SetProtocol with a value obtained from game state.

Not established here: the exact runtime SetProtocol value in v11.3.0; exact LDN advertisement payload values; game-specific Pia message fields; acceptance of a non-Switch client.

Status: Pia version family is documented; game-specific runtime values remain unknown.

2 · Offline packet inspector

Paste hex bytes from a documented packet body. Spaces, colons, and line breaks are ignored. For LDN, input must begin at the vendor-specific action-frame body, not the full 802.11 MAC header. For authentication, input must begin at the documented vendor-specific authentication payload/header. Decoder only reports fields documented by the referenced protocol page.

No packet decoded. This is an offline parser, not a network scanner.
Encrypted payloads, hashes/MAC validation, cryptographic challenges, and undocumented game fields are not decoded. A header that parses successfully does not prove the packet came from a Switch or that Splatoon will accept it.

3 · Decoder rules and known limits

  • LDN advertisement envelope: category 127, OUI 00:22:AA, protocol id 4, packet type 257 (little-endian 0x0101), documented reserved/padding fields, then advertisement payload. The payload begins with 32 bytes of session info, LDN version, encryption type, advertisement-data size, and nonce. Further fields depend on encryption type and version.
  • LDN authentication envelope: documented OUI and packet type 258, then version, payload-size pieces, status, request/response marker, reserved bytes, session info, and key/random fields. The inspector intentionally does not attempt to generate or validate authentication responses.
  • Pia LAN type byte: 0 browse request, 1 browse reply, 3 host request, 4 host message, 5 session request, 6 session message, 7 keepalive. Exact payload formats vary by Pia version; the tool identifies the type only.
  • Unknown stays unknown: no guessed offsets, no inferred Splatoon application-data schema, and no claim that Pia 5.x layouts describe Pia 6.32.3.

LDN reference: NintendoClients LDN Protocol. LAN reference: NintendoClients LAN Protocol. Version notes: Splatoon 2 and Splatoon 3.

4 · External-radio research branch

This is the next research path for a real local-wireless experiment. It is a feasibility map, not a claim that a phone-only browser can join Splatoon.

Key result: the missing capability is not a better webpage. LDN uses vendor-specific Wi-Fi action frames, which ordinary Android browser APIs do not expose for arbitrary transmit/receive. A compatible external radio plus a host-side bridge is the plausible architecture to investigate.

Path A · Phone browser only

Blocked by platform APIs

GitHub Pages JavaScript can parse saved bytes and communicate with supported peripherals through browser APIs. It cannot put the built-in Wi-Fi chipset into monitor mode, craft arbitrary 802.11 action frames, or directly access raw Wi-Fi management frames.

Verdict: keep for protocol analysis and user-interface experiments, not a real LDN radio endpoint.

Path B · External radio + bridge

Extra hardware and client code required

A current example, pokeldn, demonstrates an ESP32 radio bridge for several retail Pokémon games on Switch and Switch 2. Its published supported-game list does not include Splatoon. The Android route requires its native app and a compatible external board, not just a webpage.

Verdict: evidence that the shared radio layer is achievable in other game-specific projects, not evidence that a Splatoon 3 client exists or that JoyGPT can join a room.

Path C · Linux monitor-mode host

Different hardware setup

Existing LDN research describes Linux-side Wi-Fi channel control and monitor-mode capture. This is useful for learning and packet observation, but it requires a compatible Wi-Fi adapter and a computer environment; it is not achievable by just plugging the current phone into the Switch 2.

Verdict: a later validation route if compatible hardware becomes available.

Step 4 result · What current references actually prove

Radio API: Espressif's ESP32 Wi-Fi documentation says its raw 802.11 transmit API can send action frames, but not encrypted 802.11 frames. That is only a radio-driver capability; it does not prove a complete Nintendo LDN exchange or game compatibility. Wi-Fi frame encryption is also distinct from any encryption inside LDN payloads.

Existing external-radio project: pokeldn's current documentation describes an external ESP32 radio, USB connection, and native application that implements game-specific behavior for listed Pokémon titles. Splatoon is not in its supported-game table. It is a useful architecture reference, not a reusable Splatoon client.

Browser bridge: Chrome's Web Serial documentation describes browser-to-serial communication, while Android access depends on the browser, USB bridge, and device permissions. JoyGPT has not verified this path with an actual board on your phone.

Current verdict for your setup: phone + Switch 2 + normal browser is still not a demonstrated real-LDN setup. No radio board is available, the working Pokémon project does not implement Splatoon, and switching to an external board would not remove the need for a version-matched Splatoon client. Don't treat a generic ESP32 board or a USB cable as a ready-made solution.

🛠️ 5 · Radio hardware checklist · build 2026-10-17

This is the new update marker. If this heading appears on the published site, the new HTML reached GitHub Pages. If it does not, the problem is deployment or caching, not the radio code.

The goal is a real local-wireless research path, not a fake “connected” screen. No compatible radio board has been selected or tested yet.

Do not buy a random ESP32 or Wi-Fi dongle based on the name alone. The device must support the exact low-level radio operations needed, and we still need a Splatoon-specific client. A radio by itself cannot join a Splatoon room.

Current candidate verdicts

  • Built-in Galaxy A37 Wi-Fi: not exposed to arbitrary raw action-frame TX/RX by ordinary webpage APIs. Not a browser-only radio path.
  • Generic ESP32 board: do not assume it is enough. The referenced ESP-IDF raw TX capability has frame/encryption limitations, and no Splatoon client is known in this project. Unverified candidate, not a recommendation to buy.
  • ESP32 external-radio projects for other games: useful proof of architecture only. Their supported-game lists do not establish Splatoon support, and a native-app requirement conflicts with this browser-only setup.
  • Linux PC + compatible Wi-Fi adapter: possible later capture/research route if hardware becomes available, but it is not phone-only and capture support does not automatically mean transmit or join support.

6 · Real-connection acceptance criteria

This project only earns the label REAL JOIN VERIFIED when the evidence proves the phone's client participated in the intended Splatoon 3 local session. A decoded byte pattern, a nearby console, or a promising-looking scan is not a join.

Evidence gates

GateRequired evidencePass condition
A. Hardware pathIdentify the actual radio or supported bridge, its driver/firmware, and the documented transmit/receive capabilities.Specific hardware and API are named and independently documented; “USB connected” alone fails.
B. Observed trafficCapture traffic from a controlled, authorized setup and retain the raw bytes, capture method, timestamp, and protocol/version assumptions.Bytes are an actual capture, not a hand-entered sample; each interpretation is tied to a version-matched reference or labelled unknown.
C. Session understandingDocument the relevant discovery, host/session, and failure paths for the exact game version.Required fields and message transitions have evidence; unknown values remain unknown rather than being guessed.
D. Client participationShow that the client sends and receives the expected session traffic through the identified hardware path.Both directions are observable and correlated to one test session; a one-way advertisement does not pass.
E. Retail-console proofOn a retail Switch running the target Splatoon 3 version, show the expected room/player state and record the matching test-session evidence.The console visibly recognizes the client in the intended local room/session. Repeat the test successfully after leaving and rejoining.

Result labels we are allowed to use

  • DOCUMENTED: supported by a public protocol or hardware reference.
  • OFFLINE DECODED: the inspector interpreted supplied bytes only. No claim that those bytes were captured live.
  • LIVE TRAFFIC OBSERVED: raw frames were captured from an identified setup. This still does not prove a session join.
  • SESSION EXCHANGE OBSERVED: both directions of relevant traffic were correlated to one test session. This still does not prove the game accepted the client.
  • REAL JOIN VERIFIED: the target retail console visibly accepted the client into the expected local room, and the result was repeatable.
